# MoonDigest agent interface v1

How AI agents use MoonDigest: page messages for agents that drive the browser (the skill, `skills/moondigest/SKILL.md`), and a local MCP server (`mcp/`) for any MCP client. The page messages read the video of the page they run in and nothing else: no search, nothing of the user's account, no write. Everything else goes through the MCP server, behind one switch (§2): a video search (`search`), the user's own Bilibili favorites, follows and watch history with their 分拣 tags, notes and AI verdicts (`favorites` / `follows` / `history`), the user's collections on other sites (`collection`), and the writes: Bilibili's favorites (`favWrite`), the 分拣台's local results and 判断标准 (`triage`, `triageSettings`), which folders the 分拣台 keeps a copy of (`sync`), and the collections (`collectionWrite`). No write asks the user first. Safety is undo: every `favWrite`, `collectionWrite`, `triage`, 判断标准 change and untick is journaled and reversed by `undo`, from the tool, the 分拣台 (U) or 设置 → MCP. Never API keys or AI conversations. For sites beyond the Bilibili 分拣台 MoonDigest has no pages of its own: the agent is the UI.

Supported pages: Bilibili video pages (`www.bilibili.com/video/…`, `/bangumi/play/…`, `/list/…`, `/festival/…`) and YouTube watch pages (`www.youtube.com/watch?v=…`). The MCP server reads the sites registered in `extension/agent-sites/` (§5); the page messages only these two.

## 1. Page messages (what the skill uses)

An agent that drives a browser runs JS in the video page and talks to the extension with `window.postMessage`. Only messages whose `event.source === window` are answered (the page's own scripts, not other frames). Replies are posted to `location.origin`.

Request envelope: `{ type, id, ...params }`. `id` is any string the caller picks.
Reply envelope: `{ source: "moondigest", id, ok: true, version, data }` or `{ source: "moondigest", id, ok: false, version, error, code? }`.

- `version`: protocol version, `1`.
- `error`: a sentence for a human. `code`: a stable string when there is one (see §4).

### `moondigest-get`

Params: none. Reads the page's current video (waits for a read in flight; does not reread a video already read).

`data`:

| field | type | meaning |
|---|---|---|
| `url` | string | `location.href` |
| `site` | `"bilibili"` \| `"youtube"` | |
| `videoId` | string | BV id or YouTube id |
| `title`, `author`, `uploadDate`, `description` | string | `""` when unknown |
| `duration` | number | seconds, `0` when unknown |
| `part` | `{ index, count, title }` | Bilibili multi-part; `count` 0 = not multi-part |
| `chapters` | `[{ title, from, to }]` | seconds |
| `subtitle.segments` | `[{ from, to, content }]` | seconds; `[]` when none |
| `subtitle.lang` | string | the track's label or language |
| `subtitle.warning` | string | the subtitle's time range does not match the video |
| `subtitle.missing` | string | why there is no subtitle; `""` when there is one |
| `subtitle.needLogin` | boolean | Bilibili hides subtitles from logged-out users |
| `comments` | `[{ uname, like, message }]` | hot comments, `message` ≤ 500 chars |

### `moondigest-frame`

Params: `at` (seconds, required), `maxWidth` (pixels, optional, default 1280).

Pauses the page's `<video>`, seeks to `at`, waits for `seeked` and a decoded frame, draws it to a canvas and returns a JPEG (quality 0.85, scaled down to `maxWidth` keeping the ratio). The video stays paused at `at`. Bilibili's danmaku is not in the frame (it is drawn over the video, not into it).

On YouTube, while an ad plays (`#movie_player.ad-showing`) the frame waits: it clicks the skip button when one shows and gives up after 30 s with code `AD_PLAYING` (short enough to come back through the MCP server's 60 s).

`data`: `{ at, width, height, image }`, `at` the time actually shown (`video.currentTime`), `image` a `data:image/jpeg;base64,…` URL.

Errors: `NO_VIDEO` (no `<video>` on the page), `TAB_HIDDEN` (the tab has never been shown, so Chrome has not loaded the video), `SEEK_TIMEOUT` (no `seeked` within 15 s), `AD_PLAYING`, `FRAME_BLOCKED` (the canvas is tainted).

## 2. Extension ↔ MCP server (what the MCP uses)

Off by default. The user turns it on in 设置 → MCP → 允许 Agent 使用我的 B站和 YouTube 账号 (`mcpAccess`), the one switch: while it is on every method below is answered, reads and writes alike; there is no switch per kind of data and no code for one. While on, the extension's service worker keeps a WebSocket to `ws://127.0.0.1:47823/` (the MCP server is the listener). When the socket closes it reconnects after 5 s, then backs off to 60 s; it stops when the switch is turned off, and the server then answers every call with `NOT_CONNECTED`. The connection's state is stored as `mcpStatus` (`connected` / `disconnected` / `off`) for the settings page.

The switch used to be 允许 MCP 连接 with three switches under it (`mcpEnabled` with `mcpPersonalData`, `mcpWrites`, `mcpCollectionWrite`). The one switch has its own key, so the old connection switch never stands for reading and changing the account. On update (`background.js` `migrateMcpSwitches`) `mcpAccess` starts on only for someone who had all four on, and only while `mcpAccess` was never set; for everyone else it is off until they turn it on. The four old keys are removed, and an older version on another computer writing `mcpEnabled` again turns nothing on.

The server accepts a connection only when its `Origin` header starts with `chrome-extension://` (web pages can open WebSockets to localhost too). Any installed extension passes that check, so an extension the user installed could take the one connection and answer with made-up data; the server trusts the user's own extensions. When a second extension connects, the server keeps the first and closes the second with code 4001.

Messages are JSON text frames.

Extension → server on open: `{ type: "hello", version, extensionVersion }`. The server counts the extension as connected only after `hello`.

Server → extension: `{ id, method, params }`. Extension → server: `{ id, ok: true, data }` or `{ id, ok: false, error, code? }`.

| method | params | does |
|---|---|---|
| `get` | `{ url, brief? }` | Same `data` as `moondigest-get`, for the video at `url`; see below |
| `frame` | `{ url, at, maxWidth? }` | Same `data` as `moondigest-frame` |
| `search` | `{ site, query, page? }` | A video search on `site` (a §5 site id whose adapter has `search`: `"bilibili"`, `"youtube"`), `page` default 1; see below |
| `favorites` | `{ folderId?, page?, query?, all?, verdict?, stage?, tag?, invalid? }` | The user's Bilibili favorites, see below |
| `follows` | `{ page?, query? }` | The UP 主 the user follows, see below |
| `history` | `{ cursor? }` | The user's Bilibili watch history, see below |
| `sync` | `{ include?, exclude?, start?, folders? }` | Which folders the 分拣台 keeps a copy of, and reading those copies in the background, see below |
| `covers` | `{ bvids }` | One image: a numbered grid of those videos' covers, see below |
| `collection` | `{ site, kind, id?, cursor? }` | One page of the user's collection on `site`, see below |
| `collectionWrite` | `{ site, op, kind, id?, items, dryRun? }` | Adds items to or removes them from that collection, see below |
| `triage` | `{ items }` | Writes the 分拣台's local results, see below |
| `triageSettings` | `{ folderId?, criteria? }` | Each ticked folder's 判断标准 and tags; sets a 判断标准, see below |
| `favWrite` | `{ op, from?, to?, bvids?, folder?, title?, private?, acceptLoss? }` | Changes Bilibili's favorites at once, see below |
| `undo` | `{ id? }` | Reverses one journaled change, see below |
| `log` | `{}` | The journal, newest first, see below |

`get` on a Bilibili URL that names its video (`/video/BV…`, `/video/av…`, `/list/…?bvid=`) opens no tab (`extension/agent-video.js`): the service worker asks Bilibili through the 分拣台's channel with the functions the 细看 reads with, about a second a video, so the result is always the requested video's. Its `data` is `moondigest-get`'s with `url` the requested one, plus `zone` (Bilibili's 分区 name, may be `""`) and `tags` (the video's tags). `brief: true` is for judging many videos cheaply: `subtitle.segments` only those starting in the first 120 s, `chapters: []`, `comments: []` (up to 5 hot comments when there is no subtitle), and `brief: true` in `data`; a `get` that goes through a tab ignores `brief`. These reads run one at a time, 300 ms apart; one still queued at the deadline is `TIMEOUT`, Bilibili's risk control is `THROTTLED`. A subtitle listed by Bilibili's old `x/player/v2` (asked only when `x/player/wbi/v2` fails; it can hand out another video's) is used only when it fits the video's length, else `subtitle.missing` says so.

Every other `get` (`/bangumi/`, `/festival/`, `/list/` without `bvid`, YouTube) and every `frame` find a tab already showing that video (same site and video id; Bilibili `/video/` also the part `p`, default 1; `/list/` and `/festival/` match on the `bvid` query, else the path; `/bangumi/` on its ep/ss id). A discarded tab (no content script until shown) is never picked. Else they load `url` in the extension's own tab: at most one, opened muted with `active: false` on first need and navigated to the next video afterwards, so calls never pile up tabs. Calls that need it run one at a time, and a call still queued when the server has given up (55 s after it arrived) is dropped with `TIMEOUT` instead of loading anything. A tab that no call has answered in yet counts as the requested video only while it is still loading. The extension waits up to 50 s for that tab's content script to answer (a missing reply or one without `ok` means not loaded yet), then fails with `TIMEOUT`, before the server's own 60 s. The extension rejects any `url` that is not a supported page with code `BAD_URL`. Then they run the same handler the page messages run, in that tab's content script (`chrome.tabs.sendMessage`), so both paths return identical results. A `get` whose URL names a BV id or YouTube id is not answered with another video's data: when the page's `videoId` differs (the tab's URL changed before its page did) the page is asked again every 500 ms, until the deadline (`TIMEOUT`). A `frame` that comes back `TAB_HIDDEN` (Chrome loads no media in a tab never shown) is asked again with that tab in front, and the tab that was in front of its window is brought back afterwards, unless the user switched tabs meanwhile; `get` never switches tabs. Timeout: 60 s per call, code `TIMEOUT`.

`search` opens no tab: the service worker fetches with the user's cookies. Bilibili: the WBI-signed `api.bilibili.com/x/web-interface/wbi/search/type?search_type=video` through the same channel as 分拣台 (`triageBiliGet`). YouTube: the `www.youtube.com/results?search_query=…` page, read from its `ytInitialData`; only the result list's own videos, no shorts, ads, channels, playlists or shelves. YouTube has page 1 only (about 20 videos); a `page` above 1 is an error. Searches run one at a time, at least 2 s apart; one still queued at the call's deadline is dropped with `TIMEOUT`. HTTP 412, B站's risk-control codes and YouTube's 429 are `THROTTLED`. No results is `items: []`, not an error.

`data`: `{ site, query, page, items }`, each item `{ site, videoId, url, title, author, duration, views, uploadDate, description }`: `url` is `https://www.bilibili.com/video/BV…` or `https://www.youtube.com/watch?v=…` (ready for `get`); `title`, `author`, `description` plain text (B站's `<em class="keyword">` highlights and HTML entities removed), `description` at most 200 characters; `duration` seconds, `0` when unknown (a live stream); `views` a number or `null`; `uploadDate` B站 `YYYY-MM-DD` (local day), YouTube as the page writes it ("2 years ago", in the browser's language), `""` when missing.

`favorites`, `follows` and `history` (`extension/agent-mydata.js`) read the user's own Bilibili account in the service worker, no tab. They only GET Bilibili's read endpoints (the 分拣台's channel, `triageBiliGet`) and write nothing, to Bilibili or to storage. They run one at a time, a second apart, and return one page per call. Bilibili is asked for one page, except the folder list (up to 20 pages of folders) and 稍后再看 (all of it in one request); a ticked folder's local copy is read whole, then paged.

- `favorites` without `folderId`: `{ folders: [{ id, title, count, private?, included?, synced? }] }`, 稍后再看 first with id `"toview"`, then the user's own folders (Bilibili's folder list, read live). `count` is Bilibili's; `private` is Bilibili's 私密 (the lowest bit of the folder's `attr`); `included` means ticked in the 分拣台's 收藏夹设置; `synced`, on a ticked folder with a local copy (`triage_snapshot_<id>`), is how many videos the copy holds, and is absent while the folder has none yet. With `folderId`: `{ folderId, source, total, page, hasMore, items }`, 40 a page. A folder ticked in the 分拣台 is read from its local copy (`source: "local"`, as of its last read, no Bilibili request) without the videos 取消收藏 since that read (the copy keeps those until its next read; `triage_decisions_<id>` names them); `toview` is read whole from Bilibili in one request; any other folder is one Bilibili page (`source: "bilibili"`). `query`: words that must all appear, case-insensitive, matched on title, author, tags, note and summary for the local copy and `toview`; for other folders Bilibili's own favorites search gets it as `keyword` (titles only, and `total` is then left out). An item: `{ bvid, url, title, author, duration, favTime, invalid?, progress?, tags?, note?, verdict?, summary?, kept? }`: `tags` are the user's 分拣 tags (and 摘读记录 tags), `note` the 备注, `verdict` `keep` / `drop` / `unsure` (`MdgTagCore.verdictOf`), `summary` the 细看's one-liner, `kept` the 保留 mark, `progress` seconds watched in 稍后再看 (-1 finished).
- `favorites` with `all: true` asks Bilibili nothing: `{ all: true, source: "local", unsynced?, total, page, hasMore, items }`, the local copies of every ticked folder as one list (`folderId` limits it to one), 300 a page, each video once (`TriageCore.mergeFolderItems`, the 分拣台's 所有收藏夹; 取消收藏 ones left out as above). An item is the one above plus `folders` (the ids of every ticked folder whose copy holds it) and `stage` (`none`, `coarse`: a 粗看 verdict, `fine`: a 细看 one). Filters, all applied together: `verdict` (`none` / `keep` / `drop` / `unsure`), `stage` (`none` / `coarse` / `fine`), `tag` (one tag name the video carries), `invalid` (`true`: only videos Bilibili marks 已失效, `false`: only the others), `query` as for a local copy; a wrong `verdict`, `stage` or `folderId` is `BAD_PARAMS`. `unsynced` lists the ticked folders with no copy yet, which the list therefore lacks: `sync` reads them.
- `follows`: `{ source, total, page, hasMore, items: [{ mid, name, sign, groups, tags? }] }`, 50 a page. With a synced 关注 list (the 分拣台's 关注) it is read from there (`source: "local"`, with the user's UP 标签 as `tags`, and `query` matched on name, sign, groups and tags); else Bilibili's whole list, read by 关注分组 as the 分拣台's 刷新 reads it (`followReadGroups` in `triage/follow-bg.js`: 500 a request, about 10 requests for 4000 follows, kept 3 minutes so paging reads it once), in Bilibili's group order (`source: "bilibili"`, `query` matched on name, sign and groups). `groups` are 关注分组 names, 特别关注 and 默认分组 included.
- `history`: `{ items: [{ bvid?, url, title, author, viewAt, progress, duration, kind }], cursor }`, 30 a call, newest first. `cursor` is opaque; pass it back for the next page, `""` at the end. `kind` is Bilibili's business (`archive` for a video, also `pgc`, `live`, `article`…); `progress` is seconds, -1 finished; `viewAt` seconds since the epoch.

`collection` and `collectionWrite` (`extension/agent-collections.js`) work on any site whose adapter has `collections` (§5): Bilibili and YouTube. `kind` is one of the adapter's kinds, else `UNSUPPORTED_KIND`; Bilibili has `watch_later` (稍后再看, `add` and `remove`; its favorites, follows and history stay in `favorites`, `follows`, `history`), through `triage/triage-bg.js`'s own 稍后再看 requests in the service worker; YouTube has `watch_later`, `playlists`, `playlist` (with `id`), `likes`, `subscriptions`, `history`, and writes to `watch_later` and `playlist` only (`add`, `remove`). Calls run one at a time, a second apart, and stop with `TIMEOUT` while still queued at the deadline.

- `collection`: `data`: `{ site, kind, id?, items, cursor }`, `cursor` `""` at the end, else passed back for the next page. A video `{ videoId, url, title, author, duration, unavailable? }` (`duration` 0 when unknown), a playlist `{ id, title, count? }`, a channel `{ channelId, url, title }`.
- `collectionWrite`: `items` 1 to 20 distinct ids (Bilibili: BV ids; YouTube: video ids), else refused before any request. `dryRun: true` writes nothing. The items go one at a time, 1.5–3 s apart (random): the item's state is read first and an item already as asked is skipped (`unchanged`); otherwise a dry run reports `would_change`, a real run writes, waits 1 s and reads again (`done`, or `unconfirmed` when the read still shows the old state). A YouTube write is `done` on YouTube's own answer (`STATUS_SUCCEEDED`, else `failed`) with no read after: its state read lags writes by about 12 s. For 30 s after a write the item counts as written, so an undo right after is not skipped as already so. `THROTTLED` (429, a captcha page) or `NOT_LOGGED_IN` (no login, or 403: the login or the request's signature not accepted) stops the batch; another error fails only its item (`failed`). An item is not started with less than 12 s left before the call's deadline, nor its write sent with less than 22 s left (time for the write and the read that confirms it); each youtubei request ends within 10 s and by the deadline (`stopped: "TIMEOUT"`): call again with `notDone`, which is safe since done items are skipped. `data`: `{ site, op, kind, id?, dryRun, results: [{ item, status, before?, after?, error? }], done, notDone, stopped?, undoId?, undo }`, `undoId` its journal entry (a real run that sent at least one write), `undo` the `collectionWrite` params that reverse every item whose write went out (`done`, `unconfirmed`, and `failed` after the write was sent, which may have landed; undo reads each first and skips the ones that had not), or `null`. Undo is not exact: an item removed and added back goes to the end of the playlist (YouTube adds at the end), and a video a playlist held more than once is removed by its id and added back once. No confirmation token between a dry run and the run: the agent makes both calls, so a token would check nothing a dry run does not; the cap, the skip and the undo are the safety. These writes are not in the journal below: their undo is the returned call.
- YouTube: youtubei calls (`browse` with browseId `VLWL`, `VL<id>`, `VLLL`, `FEplaylist_aggregation`, `FEchannels`, `FEhistory`, and `continuation` for later pages; `playlist/get_add_to_playlist` for an item's state, the Save dialog's list of the user's own playlists; `browse/edit_playlist` with `ACTION_ADD_VIDEO` / `ACTION_REMOVE_VIDEO_BY_VIDEO_ID`) made in the bridge's own tab on a youtube.com page (any YouTube page it already shows, else `https://www.youtube.com/`), in the page's MAIN world, with the page's `ytcfg` context and the `SAPISIDHASH` authorization yt-dlp computes (`_get_sid_authorization_header`). Never in the user's tabs. A service worker fetch cannot make these calls: it carries the extension's `Origin`, which fetch cannot change. The endpoint and field names come from yt-dlp and public client code; they are tested against hand-written answers only, not against YouTube.
`sync` (`extension/agent-sync.js`) is the 分拣台's 收藏夹设置 for a tool: which folders are ticked (`triage_included_folders`), and reading the ticked folders' copies from Bilibili in the service worker, without the 分拣台 page open. `include` / `exclude` are folder ids (`toview` too) to tick and untick; an id in both, and an `include` or `folders` id that is not one of the user's folders, is `BAD_PARAMS`. Ticking reads nothing by itself (`start` does). Unticking is journaled (kind `scope`) and `undo` ticks the folders again and has a cost the answer's `notes` spell out: the next time a 分拣台 page is open it removes that folder's copy and its 取消收藏 records, and the folder's videos that are in no other ticked folder go to 已出分拣范围 (`retireUnchosenFolders`). AI verdicts, notes, 保留 and tags are kept: they belong to the video, not the folder. `start: true` starts one background job over the ticked folders (or the ticked ones among `folders`; an unticked one is named in `notes` and not read) and answers at once; a job already running is not doubled (`notes` says so). The job takes one folder at a time: when the copy's id list still equals Bilibili's (one request) the folder is `unchanged`, else it is read whole and saved through `MdgFavRecords.saveNow`, as the page saves it; a list Bilibili cut short is not saved (`partial`). Between folders it waits 收藏夹设置's 请求间隔 (300 ms after an unchanged one). `THROTTLED` ends the job. `data`: `{ folders, job?, notes? }`, `folders` as `favorites` lists them, `job` `{ running, total, done, current, read, unchanged, partial, stopped?, error? }`: `total` / `done` count folders, `current` is the folder being read, `read` and `unchanged` count results, `partial` lists the folder ids not saved, `stopped` is `"THROTTLED"`, `error` another failure's text. The job lives in the service worker's memory: a worker Chrome restarted has no job (no `job` in the answer) and what it had not read stays unread, so call with no parameters to follow it and start again when `synced` is still missing.

`triage`, `triageSettings`, `favWrite`, `undo` and `log` (`extension/agent-writes.js`) run one at a time in one queue, so two Bilibili batches never run at once and an undo never overtakes the write it reverses. The extension checks every parameter before writing anything (`BAD_PARAMS`: a bvid is `BV` and 10 letters or digits, a folder id is digits or `toview`, lengths as below). Each call that changed something adds one entry to the journal (`triage_agent_log`, the last 100 changes on Bilibili and YouTube and the last 100 local ones, oldest dropped) and answers with its id as `undoId`; when the journal itself could not be written the change stays and the answer carries `noUndo: true` instead. A change that failed midway keeps and journals what landed, and the error says so.

- `triage`: `items`, 1 to 50 of `{ bvid, verdict?, coarse?, confidence?, summary?, reason?, points?, kept?, note?, folderId?, addTags?, removeTags? }`, each bvid once; only the fields given change. `verdict` (`keep` / `drop` / `unsure`) comes in two shapes. Read (the tool went through the video): it needs `summary` (≤ 100 chars), `reason` ≤ 300, `points` ≤ 3 of ≤ 200, and is stored as a 细看 result (`triage_analysis_<bvid>`, `source: "agent"`; the card says Agent 判断). `coarse: true` (judged from the title, tags or cover alone): it needs `reason` (≤ 300), takes `confidence` (`high`, the default, or `low`) and no `summary` or `points`, and is stored as a 粗看 result (`triage_title_<bvid>`, `model: "agent"`), which a later 细看 overrides as it does the 分拣台's own 粗看. `kept` sets or clears the 保留 mark; `note` (≤ 2000, `""` removes it) the 备注; `addTags` / `removeTags` (≤ 10 names each) the tags of folder `folderId`, which must be ticked and whose local copy holds the video. A missing tag is made while the folder is under 收藏夹设置's tag cap; the others are answered in `tagsNotMade`. Each key is read-modify-written under the lock the 分拣台 takes for it (`MdgLimits.update`, `saveVideoNote`, `keyLock(triage_tags)` for the tag list and map), so neither side loses the other's write. Nothing changes on Bilibili. `data`: `{ changed, undoId?, tagsNotMade?, noUndo? }`.
- `triageSettings`: without `criteria`, `{ folders: [{ id, title, criteria, tags: [{ name, rule?, videos }] }] }` for every ticked folder, or the one `folderId` names: its 判断标准 (`""` when none), and each of its tags with the tag's rule and how many videos carry it. With `folderId` and `criteria` (≤ 1000 chars, `""` removes it) it sets that folder's 判断标准 (`triage_folder_criteria`) first, and the answer adds `changed: { folderId, was, undoId? }`; the same text again changes and journals nothing. Results judged by the old 判断标准 then count as stale in the 分拣台, so the tool is told to tell the user.
- `favWrite`: `op` decides the rest. It sends Bilibili's own requests through `triage/triage-bg.js`'s handlers, the ones the 分拣台 sends to, and then updates the local records through `extension/triage/fav-records.js` (`MdgFavRecords`), the functions the 分拣台 page updates them with: the folders' cached lists, 已出分拣范围, the left trail and the 取消收藏 records.
  - `move` / `copy`: `bvids` (1 to 500, each once) from folder `from` (or `toview`) to folder `to` (not `toview`, not `from`). `unfav`: `bvids` out of `from`. `clean_invalid`: out of `from` (not `toview`) every video its local copy marks 已失效, up to 500 a call; without a copy it is `BAD_PARAMS`. When MoonDigest has a copy of `from`, every bvid must be in it (else `BAD_PARAMS` naming them: the copy is stale or the id wrong, `sync` reads it again); without a copy the video's aid is computed from its BV id.
  - The videos go 20 a request, 1 s apart (from 稍后再看 one a request, 300 ms apart). The run ends early when less than 8 s of the call's time are left (`stopped: "TIMEOUT"`: send `notDone` again) or Bilibili rate-limits (`stopped: "THROTTLED"`, which the MCP server returns as an error: stop). `data`: `{ op, from, to?, done, notDone, stopped?, undoId?, noUndo? }`, `done` and `notDone` bvids. Another failure is an error whose text says how many were done before it; those are journaled too.
  - `folder_create` (`title` ≤ 20 chars, `private`), `folder_rename` (`folder`, `title`), `folder_privacy` (`folder`, `private`), `folder_delete` (`folder`); none takes `toview`. `data`: `{ op, folder, title?, hiddenLost?, undoId?, noUndo? }`, `folder` the id (the new one for `folder_create`). The stored folder list (`triage_folder_list`) follows, a rename also the copy's title, a delete also unticks the folder.
  - `folder_delete` first reads the folder's info and its whole list. A list that cannot be read whole is `NETWORK` and nothing is deleted. Bilibili's count can exceed what its list returns (videos deleted there stay counted, unseen): when it does and `acceptLoss` is not `true`, nothing is deleted and the call fails with `HIDDEN_ITEMS`, naming the count, the listed number and the difference, which no undo can bring back. With `acceptLoss: true` it deletes, and `hiddenLost` is that difference.
- `undo`: `id` is an `undoId`; without it the newest entry. The entry stays in the journal while it is undone, marked (`undoing`, for two minutes), so a second undo of it meanwhile is refused and a background that dies midway loses nothing; it leaves the journal when all of it is undone, and what could not be undone stays under the same id. `data`: `{ id, n, skipped, failed?, left?, stopped? }`: `n` videos put back, `skipped` values left alone because they changed since, `failed` videos Bilibili said no to (a deleted video, a full list): the undo goes on with the others and those stay in the entry (`left`, `stopped: "REFUSED"`), so nothing is forgotten. A request that only failed (HTTP 500, no JSON) is an error, and the entry keeps everything not yet undone. Per kind of entry:
  - `triage`: each value still as the tool left it goes back to what it was before (a result the 分拣台 stamped with its 判断标准 on open counts as unchanged); one the user changed since stays and counts in `skipped`. Tags the call made that nothing carries any more are removed.
  - `criteria`: the folder's 判断标准 goes back to the earlier text, unless it is no longer the text the tool set (`skipped: 1`).
  - `fav`: on Bilibili. `unfav` and `clean_invalid`: each video is favorited into `from` again, one request a video (Bilibili has no batch for it). `move`: the videos move back from `to` to `from` (into 稍后再看 one at a time: added back, then taken out of `to`). `copy`: they are taken out of `to`. The entry's `had` lists the videos `to` already held before the call (by Bilibili's id list, asked before the write: a copy may be behind): those stay in `to`; after a `move` they are copied back to `from`, after a `copy` nothing is done for them.
  - `folder`: `folder_create` deletes the folder, unless it holds videos by now (an error, nothing deleted). `folder_rename` and `folder_privacy` set the earlier title or privacy. `folder_delete` makes a new folder with the old title and privacy and favorites the listed videos into it, oldest first so the order comes out as it was. It is a new folder with a new id: the old id is gone, the folder is not ticked again, and the videos Bilibili counted but did not list are lost.
  - An undo on Bilibili has the same limits as a write: when the call's time runs out or Bilibili rate-limits, it answers `left` (videos still to do) and `stopped` (`"TIMEOUT"`, `"THROTTLED"`, `"NOT_LOGGED_IN"`, or `"REFUSED"` when the site said no to the videos left, a deleted video or a full list: they stay in the entry), and the entry stays in the journal under the same id with only those videos (a deleted folder's entry remembers the folder it already made), so `undo` with that id goes on where it stopped. After `THROTTLED`, later, not at once.
- `log`: `{ entries }`, newest first, each `{ id, at, kind, op?, n, titles?, folder?, was?, title? }`: `kind` `triage` / `fav` / `folder` / `criteria` / `collection` (a `collectionWrite`, whose result carries its `undoId`; undone by the reverse write, each item read first) / `scope` (folders unticked by `sync`, kept with their 取消收藏 records; undone by ticking them again and putting back the records the 分拣台 dropped), `op` the `favWrite` or `collectionWrite` op, `n` the videos, `titles` `{ from, to? }` the folder names at the time, `was` / `title` a folder's earlier and later name. The MCP tool `undo` with `list: true` calls it.

The same undo runs for the user, whatever the switch says at the time (they take back what was written while it was on), through the runtime message `agent-undo` `{ id }`: the 分拣台 shows every journal entry as a U step (asking first when it covers more than one video), and 设置 → MCP lists the journal under Agent 最近的修改 with 撤销 per entry. While the answer has `left`, 设置 → MCP calls again until it is done or `THROTTLED`; in the 分拣台 the step stays and the next U goes on.

`covers` (`extension/agent-covers.js`) draws the covers of `bvids` (1 to 16 distinct BV ids, else `BAD_PARAMS`) into one JPEG in the service worker, no tab: 4 columns of 320×200 cells in the order of `bvids`, each with its number (from 1) on a dark box at its top-left. The cover URLs come from the 分拣台's local copies (every `triage_snapshot_*`, then `triage_removed`), with no Bilibili API request; only the images are fetched, from the image CDN (`*.hdslb.com`, a 320×200 rendition), at most 4 at a time, 8 s each, all given up 2 s before the call's deadline. A video the copies do not have, one without a cover and one whose image does not load are grey cells, still numbered, with `missing: true`. `data`: `{ image, width, height, cells: [{ n, bvid, title, missing? }] }`, `image` a `data:image/jpeg;base64,…` URL, `title` `""` when unknown.

Keepalive: the server sends `{ type: "ping" }` every 20 s and the extension answers `{ type: "pong" }` (WebSocket traffic keeps an MV3 service worker alive in Chrome 116+).

## 4. Codes

`NOT_VIDEO_PAGE`, `TAB_HIDDEN`, `THROTTLED` (Bilibili 412 / YouTube 429: stop, do not retry soon), `NO_VIDEO`, `SEEK_TIMEOUT`, `AD_PLAYING`, `FRAME_BLOCKED`, `BAD_URL`, `NO_ACCESS` (MoonDigest has no access to that site, §5), `NOT_CONNECTED` (MCP server: no extension connected: the browser is closed, or 设置 → MCP's switch is off), `TIMEOUT` (no answer within the call's time, or the call waited too long behind earlier ones), `BAD_PARAMS` (a parameter is wrong, the error says which; nothing was asked or written), `HIDDEN_ITEMS` (`favWrite` `folder_delete`: Bilibili counts videos it does not list; nothing was deleted, `acceptLoss: true` deletes anyway), `NOT_LOGGED_IN` (not logged in to the site in that browser), `NETWORK` (the site did not answer), `OUTDATED_MCP` (the server asked for a method this extension dropped, `propose`: the MCP server is older than the extension and must be updated, by adding it again with the command 设置 → MCP shows; the other way round, an extension older than the server answers `Unknown method …` and the server adds that the extension must be updated), `PORT_IN_USE` (MCP server: another moondigest-mcp holds the port; it takes over when that one exits), `UNSUPPORTED_KIND` (the site has no such collection, or it is read only).

The port is fixed at 47823 on both sides. The server's `MOONDIGEST_MCP_PORT` is for tests only.

## 5. Sites

Each site the MCP server reads is one adapter, `extension/agent-sites/<id>.js`, registered with `extension/agent-sites/registry.js`. `agent-bridge.js` and `agent-search.js` ask the registry and name no site. Sites beyond Bilibili and YouTube get MCP tools only, no pages of their own.

```js
MdgAgentSites.register({
  id: "demo",                         // [a-z0-9-]+, the MCP `site` value
  origins: ["https://www.demo.com/*"], // match patterns: the user's tabs to look in, the host access to check
  key(u) {                            // u: a URL; "itemId:part" for a page this site reads, else null
    const m = /^\/v\/(\w+)$/.exec(u.pathname);
    return u.hostname === "www.demo.com" && m ? `${m[1]}:` : null;
  },
  read: "content",                    // the content script (agent-page.js) answers in the page
  search: async (query, page) => [],  // optional: §2's search items, throw an Error with code THROTTLED when rate-limited
  // optional, all four together: the user's collections (§2 collection / collectionWrite)
  collections: { saved: ["add", "remove"], history: [] }, // kind → the writes it takes ([] read only)
  list: async ({ kind, id, cursor }, deadline) => ({ items: [], cursor: "" }),
  has: async ({ kind, id, item }, deadline) => false,        // is item in it now
  write: async ({ op, kind, id, item }, deadline) => {},     // one item; agent-collections.js reads before and after
});
```

- `canonical(u)` (optional): the page to load for another form of the site's URL (YouTube: `youtu.be`, `/shorts/`, `/live/`, `m.` and `music.youtube.com` → `www.youtube.com/watch?v=…`; Bilibili: `m.bilibili.com` and `bilibili.com` → `www.bilibili.com`, same path; `b23.tv` short links are not followed), else null. The bridge applies it to the requested `url` only, never to tabs.
- `key`: the registry prefixes the id, so two URLs of one video must give the same `itemId:part`. Two keys equal means the same video for tab reuse.
- `read: "content"`: a content script (`agent-page.js`) answers in the page. It needs a manifest entry and host access, which the manifest grants for Bilibili and YouTube.
- `list`, `has`, `write`: agent-collections.js has checked the kind, the op and the items before; the adapter writes one item per `write` and never batches, retries or skips (the rules in §2 are agent-collections.js's). Throw an Error with code `THROTTLED` or `NOT_LOGGED_IN` to stop a batch. To run in the site's page, `MdgAgentBridge.inSitePage(site, url, ready, func, args, deadline)` runs `func(...args)` once in the MAIN world of the bridge's own tab on a page of `site` (loading `url` there when it shows another site), after `ready()` there returns `{ ok: true }`. Both are serialized (`chrome.scripting.executeScript`): no closures, no extension globals; write them as arrows, since a method shorthand's source does not compile there. One that does not settle by the deadline is `TIMEOUT`, and the own tab goes to `about:blank`. `func` runs once even when it fails, so it should catch and return its errors.
- A new site adds: `agent-sites/<id>.js`, `agent-sites/<id>.selftest.js` (`require("./registry.selftest.js").load("<id>.js")` gives a registry with only that site loaded), one `importScripts("agent-sites/<id>.js")` line in `background.js`, and its name in the MCP tools' descriptions (`mcp/server.js`). A `search` that reads `MdgErrors.CODE` also needs a line in `entry-matrix.selftest.js`'s `NOT_ENTRIES`.
